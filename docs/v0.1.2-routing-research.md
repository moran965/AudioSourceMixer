# v0.1.2 应用路由实现与验证

## 已采用接口

普通 Windows 应用路由使用 Windows 内部运行时类：

`Windows.Media.Internal.AudioPolicyConfig::SetPersistedDefaultAudioEndpoint`

ABI 的最小实现来自当前 EarTrumpet 源码核对，而不是非来源明确的博客片段。核对版本为 EarTrumpet commit `aa894e51c22f5f9a939b31b224c4d2d3e163416e`：

- Windows build >= 21390：IID `AB3D4648-E242-459F-B02F-541C70306324`。
- build 17134–21389：IID `2A59116D-6C4F-45E0-A74F-707E3FEF9258`。
- IInspectable 六个基槽位加十九个前置方法，因此 Set/Get 为 vtable slot 25/26。
- HSTRING 设备形式为 `\\?\SWD#MMDEVAPI#<MMDeviceId>#{e6327cad-dcec-4949-ae8a-991e976a79d2}`。

实现通过 `RoGetActivationFactory` 获取原始接口指针，显式创建/释放输入 HSTRING，并释放 Get 返回的 HSTRING。它不调用全局 `ClearAllPersistedApplicationDefaultEndpoints`。

## 事务与验证

每次修改前读取 Console、Multimedia、Communications 原值。写入和恢复固定采用 Multimedia → Console → Communications；本机 build 26200 在清空共享 Console/Multimedia 策略时若先写 Console 会返回 `E_ACCESSDENIED`。三个 role 全部成功后立即读回；任一写入失败会按相同安全顺序逐 role 写回原值。策略读回成功后，服务聚合同应用在全部 `EndpointContext` 上的活动会话；全部位于目标并稳定 750 ms 才返回 Applied。没有活动流、旧流仍在原端点或只有部分 sibling 已迁移分别保持 PendingStreamRestart/Partial，不做固定超时回滚。

“系统默认”使用每应用策略的空 endpoint 语义，而不是把当时默认设备 ID 固化为偏好。非默认设备断开时不清空已确认的应用策略，状态进入 Disconnected；设备恢复后后台重新观察策略与活动流，不从会话刷新路径重复写策略。

## 当前机器实测

环境：Windows build 26200 x64；默认 WH-1000XM5；另有 Realtek(R) Audio。

对正在播放的 PotPlayer PID 30108 执行只读和迁移探针：三个 role 原始值均为系统默认；设置 Realtek 后三个 Set 与策略回读均为 S_OK，WH 活动会话消失/变为 inactive，Realtek 出现同 PID active 会话；写回三个空 endpoint 后，活动会话回到 WH。探针最终 `restoreMatched=true`。

这证明了策略写入和真实 Core Audio 会话迁移，不等同于人工耳听声学确认。对一个已经打开设备的传统 WaveOut 流，策略虽成功写入，五秒内现有流仍留在原 endpoint；AudioPolicyConfig 是持久的进程默认策略，并不保证强制重建所有旧式已打开流。产品不会把“策略写成功”误报为 Applied，也不会撤销正确策略：它返回 PendingStreamRestart，并提示暂停/恢复或重开应用。系统默认随动和人工“只从目标物理设备发声”仍在最终硬件矩阵中单独记录。

## 风险隔离

这是未公开 Windows ABI，可能随系统版本变化。运行时按 build 选择已核对 variant；激活失败只关闭普通应用路由能力，不影响原生音量；日志记录 build、ABI、PID、原/请求 endpoint、每 role HRESULT 和完整错误。恢复通过 PID、可执行路径和进程开始时间检查，避免 PID 复用误改。
