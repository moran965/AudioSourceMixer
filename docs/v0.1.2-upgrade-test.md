# v0.1.1 → v0.1.2 原位升级测试

## 实际结果

测试基线是机器原有正式 v0.1.1：FileVersion 0.1.1.0，主程序 SHA-256 `CB21509C984D7FDC684242F8CA4CF795BE30F7C985D8880878AB18880C352E7B`，扩展 manifest 0.1.1，单一卸载项与 Chrome/Edge Native Messaging 注册均存在。

第一次真实原位升级没有先卸载 v0.1.1。0.1.2 安装器成功完成同级 staging、旧目录 backup、新目录固定路径提交和 backup 删除；检查结果：

- 固定安装目录只有一个，无 `.installing.*`/`.backup.*`。
- v0.1.1 sentinel 消失，安装文件集合严格等于本次 portable payload 加 uninstaller/native manifest。
- 卸载项唯一且 DisplayVersion=0.1.2；Chrome/Edge Native Host 指向新 manifest。
- publish、portable、installed 当次哈希均为 `05557EA821F409D68D772D70E65DB3995C1EF714FF8E3E0D510BA9F3A6132C50`。
- installed UI smoke 通过；普通启动日志为 `Sources=5; MaterializedItems=5`。

之后 legacy profile 迁移断言失败。原因不是目录升级，而是验证脚本用 Windows PowerShell 写出带 UTF-8 BOM 的 JSON，而 `JsonAudioProfileStore` 的字节解析未跳过 BOM。失败清理按计划卸载了 0.1.2，用户数据备份随后恢复；但旧 build-all 的数组参数传递没有真正把临时 v0.1.1 安装器路径绑定到命名参数，因此没有回装 v0.1.1。这一恢复脚本缺陷已修复为显式命名参数调用。

应用现已支持有/无 BOM 的 v1 配置，两种自动测试均通过；最终主程序哈希变为 `915ECFDE71B918A1A0C681D13C970779E4B68B92A7094ECAC4A03E8FF4E28158`。该最终构建完成 fresh silent install、legacy 0.75→75% 迁移、三份哈希、installed UI smoke、普通窗口、正常退出、静默卸载和注册表清理，但由于正式 v0.1.1 基线安装器已随前述清理消失，无法再次执行最终字节的原位升级。

结论：安装器的真实 0.1.1 目录升级路径曾通过，最终构建的迁移/fresh install 通过；“最终精确 0.1.2 字节从 v0.1.1 原位升级”仍未达到严格验收标准。

## 当前脚本保护

`scripts/verify-installer.ps1` 与 `build-all.ps1` 现在：

- 在清理 artifacts 前把正式 v0.1.1 安装器或其同构 uninstaller 复制到唯一临时目录并校验 SHA-256。
- 使用显式 `-BaselineInstallerPath` 参数传递，不再数组模拟命名参数。
- 只接受 FileVersion/manifest/卸载项均为 0.1.1 的 upgrade baseline。
- 全量备份用户数据并比较相对路径与哈希；失败时卸载候选、回装 0.1.1、恢复数据。
- 没有基线时只可显式 `-FreshInstallOnly`，manifest 写明 `inPlaceUpgrade=not executed in this invocation`，不冒充升级。
